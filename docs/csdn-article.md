# 初级嵌入式工程师如何建立底层直觉：AI 代码讲解插件实践

> 本文介绍一个面向嵌入式 C/C++ 工程的开源 AI 代码讲解插件：`explain-c-module`。它不只解释代码“做了什么”，还帮助初级工程师理解调用链、RTOS、驱动、中断、DMA、低功耗和硬件交互背后的设计原因。

## 一、为什么“看懂代码”仍然不会开发？

AI 编程工具让初级工程师很快就能看懂一段函数：输入是什么、调用了哪个 API、返回值代表什么。但真正接手一个嵌入式工程时，困难通常不在某一行代码，而在这些问题：

- 这个函数是谁调用的？运行在哪个任务或中断上下文？
- 数据经过哪些队列、回调、DMA 缓冲区，最终到达哪个外设？
- 为什么这里要关中断、加锁、延迟，或者使用环形缓冲区？
- 设备进入睡眠前关闭了哪些时钟和电源域？唤醒后恢复顺序为什么不能颠倒？
- 一个看似简单的宏、函数指针或 `container_of`，解决了什么工程问题？
- 如果去掉这一步，系统会出现什么故障？

这些内容构成了嵌入式开发中的“底层直觉”。它们很难通过逐行翻译代码获得，必须结合架构、运行时上下文和硬件约束来理解。

## 二、普通 AI 问答的不足

直接把一个 C 文件交给 AI，通常可以得到一份不错的代码摘要，但仍存在几个问题：

1. **上下文不完整**：只看单个文件，容易遗漏头文件、构建脚本、调用者和配置宏。
2. **调用链不清晰**：文字描述很快变成长段落，难以看出入口、回调和线程关系。
3. **事实与推测混在一起**：AI 可能把“常见设计”误写成“当前工程行为”。
4. **缺少反事实解释**：知道“这里加锁”，却不知道“不加锁会怎样”。
5. **文档不可复用**：一次问答结束后，知识没有沉淀为团队可评审的文档。

因此，嵌入式代码讲解需要一套稳定的方法，而不是每次重新组织提示词。

## 三、explain-c-module 是什么？

`explain-c-module` 是一个可用于 Claude Code、Codex 以及其他支持 `SKILL.md` 的 Agent 的开源插件/skill。

它的目标是把一个 C/C++ 文件或目录转换为一份适合学习、交接和代码评审的文档：

- 说明模块职责和边界；
- 梳理函数调用链、线程、任务和中断关系；
- 分析驱动、DMA、队列、回调和资源生命周期；
- 解释 RTOS、内存、时钟、电源域和低功耗流程；
- 对函数指针、`container_of`、`__attribute__` 等语法进行展开讲解；
- 用“为什么这样写”和“如果不这样写会怎样”建立工程直觉；
- 输出 Markdown 源文档和交互式 HTML 阅读版。

## 四、整体工作流程

```text
指定 C/C++ 文件或目录
          │
          ▼
读取源码、头文件、构建脚本和日志
          │
          ▼
提取调用链、线程、中断、资源和硬件上下文
          │
          ▼
生成 Markdown + HTML 学习文档
          │
          ▼
review-explain-doc 只读审核
          │
          ├── PASS：交付文档
          └── NEEDS_REVISION：修订后最多再审核 1 次
```

在 Claude Code 中，可以通过 commit Hook 自动触发；在 Codex 中，可以手动调用 skill，或者配置可选的全局 `PostToolUse` Hook。

## 五、一次手动使用

安装后，在 Agent 对话中直接提出类似请求：

```text
用 explain-c-module 分析 drivers/uart/，重点说明中断入口、DMA 缓冲区、回调链和并发风险，生成中文 Markdown 和 HTML 文档。
```

也可以分析低功耗模块：

```text
分析 power/ 目录的睡眠、唤醒、suspend/resume 和时钟/电源域关系，给出状态图和数据流图。
```

生成结果默认放在：

```text
doc/explain/md/<模块名>.md
doc/explain/html/<模块名>.html
```

## 六、它重点讲什么？

### 1. 调用链和运行上下文

嵌入式函数不能脱离上下文理解。例如一个 UART 接收函数，可能由以下链路触发：

```text
UART 外设
   │ 中断
   ▼
ISR
   │ 投递消息/释放信号量
   ▼
接收任务
   │ 读取环形缓冲区
   ▼
协议解析
   │ 回调
   ▼
业务模块
```

文档会说明每一层的职责，以及哪些代码运行在 ISR、任务或普通线程上下文中。这样才能理解为什么 ISR 中不能执行阻塞操作，为什么需要 `FromISR` 版本 API，为什么 DMA 缓冲区不能随意放在栈上。

### 2. RTOS 与并发

重点关注：

- 任务优先级和调度关系；
- 队列、信号量、事件组和互斥锁；
- 中断与任务之间的同步；
- 临界区和内存可见性；
- 超时、错误恢复和任务退出路径。

讲解不只停留在 API 名称，而是回答：这个同步原语保护的共享资源是什么？如果删除它，最小复现路径是什么？

### 3. 驱动、DMA 和资源生命周期

驱动代码经常同时管理硬件寄存器、DMA 描述符、缓存、回调和设备状态。文档会把资源生命周期串起来：

```text
设备初始化
   ↓
申请/配置 DMA 缓冲区
   ↓
启动传输
   ↓
中断或轮询完成
   ↓
刷新 Cache / 校验长度
   ↓
回调上层
   ↓
停止设备并释放资源
```

对于 Cache 一致性、缓冲区对齐和所有权转移等硬件相关结论，如果源码和芯片手册没有证据，文档会明确标注“需要查 RM 或实测”，避免把经验猜测写成确定事实。

### 4. 低功耗、suspend 和 resume

`suspend` 通常表示系统或设备进入挂起前的保存、停机和省电处理；`resume` 表示从挂起状态恢复运行。它们不等于“重启”：重启会重新执行启动流程，而 resume 通常需要恢复原有上下文。

典型流程如下：

```text
运行态
  │ suspend
  ▼
保存寄存器/关闭外设/关时钟/降电压
  │
  ▼
睡眠态
  │ 唤醒源触发
  ▼
恢复电源域/时钟/寄存器/缓存
  │ resume
  ▼
运行态
```

对于 JPEG、ADC、显示、传感器等模块，是否能关闭不能只看“功耗高不高”，还要看：

- 它是否属于当前睡眠模式必须保持的电源域；
- 是否是唤醒源或唤醒链路的一部分；
- 是否需要保留寄存器和 DMA 状态；
- 恢复顺序是否依赖时钟稳定或电源稳定；
- 关闭后是否会丢失采样、帧缓存或校准状态。

这类分析正是 AI 代码讲解与普通代码摘要的区别。

## 七、文档审核子 agent 解决什么问题？

生成文档之后，插件可以调用 `review-explain-doc` skill 或只读审核子 agent 做质量检查：

- 结论是否能追溯到源码、日志、构建脚本或手册；
- 调用链方向是否正确；
- Markdown 与 HTML 是否表达了同一结论；
- Mermaid 图是否能渲染、节点是否与正文一致；
- 文件路径、函数名和行号是否仍然有效；
- 是否把未经验证的硬件推测写成事实；
- 是否泄露密钥、账号或本地敏感路径。

审核只读源码和文档，不修改源代码、不提交 Git。审核结果使用统一格式：

```text
审核状态：PASS / NEEDS_REVISION
事实准确性：4/5
结构完整性：5/5
图表一致性：4/5
初学者可读性：4/5
可维护性：5/5
```

最多进行两轮审核，避免生成—审核—提交—再次触发的无限循环。

## 八、Claude Code 和 Codex 的差异

| 能力 | Claude Code | Codex |
|---|---|---|
| 手动调用 skill | 支持 | 支持 |
| Commit 后自动触发 | 插件 Hook 原生支持 | 需配置全局 `PostToolUse` Hook |
| 文档审核 | 支持审核 skill/子 agent | 支持审核 skill/子 agent |
| 未配置 Hook 时 | 仍可手动使用 | 仍可手动使用 |

Codex 的 Hook 安装方式：

```powershell
node <插件目录>/scripts/install-codex-hook.cjs
```

插件清单不会直接声明 Codex Hook，而是提供配置模板和显式安装脚本，避免覆盖用户已有的全局 Hook 配置。

### Git 更新后的自动生成与审查闭环

commit Hook 只能覆盖当前工作区产生的提交；团队从远程仓库执行 `git pull`、merge 或 rebase 后，
同样可能引入新的 C 代码。插件现在提供仓库级 Git 更新 Hook：

```bash
node <插件目录>/scripts/install-git-update-hook.cjs
```

安装器以非破坏方式追加 `post-merge` 和 `post-rebase`，由
`scripts/explain-update.cjs` 完成以下流程：

1. 比较 `ORIG_HEAD..HEAD`（失败时回退到 `HEAD~1..HEAD`）；
2. 只筛选 C/C++ 文件（单次最多 30 个，纯文档变更不会再次触发）；
3. 调用 `codex exec`，依次执行 `explain-c-module` 增量生成和 `review-explain-doc` 审查；
4. 要求只修改 `doc/explain/`，不改源代码、不自动提交，并返回审查状态。

支持 `EXPLAIN_C_MODULE_UPDATE_DRY_RUN=1` 试运行、
`EXPLAIN_C_MODULE_UPDATE_ENABLED=0` 临时禁用，以及
`EXPLAIN_C_MODULE_UPDATE_MODEL` 指定模型。这样可以把“拉代码”与“更新知识库”连接起来，
又不会把未经审查的文档自动合入主分支。

## 九、适用场景与不适用场景

适合：

- 新人接手大型 SDK、RTOS 或驱动工程；
- 梳理启动流程、低功耗、睡眠唤醒和设备恢复；
- 代码评审前生成模块级背景文档；
- 把隐含在老员工经验中的“为什么”沉淀下来；
- 形成 Markdown/HTML 形式的团队知识库。

不适合替代：

- 编译器、静态分析器和单元测试；
- 芯片参考手册对寄存器位的最终确认；
- 实际烧录、功耗测试和示波器验证；
- 对生产系统进行未经审核的自动修改。

## 十一、结语

AI 可以快速解释代码，但工程直觉仍然需要被系统地训练。真正有价值的代码讲解，不是把每一行翻译成中文，而是把代码放回它的运行上下文中：谁调用它、谁依赖它、它保护什么资源、它为什么必须这样设计，以及删除这一步会造成什么后果。

`explain-c-module` 的定位，就是把这种“手把手开发式”的讲解方法固化成可复用的 Agent skill，并通过 Markdown、HTML 和审核流程沉淀为团队资产。

如果你正在维护一个 RTOS、驱动或低功耗工程，可以从一个最难读的模块开始尝试。
